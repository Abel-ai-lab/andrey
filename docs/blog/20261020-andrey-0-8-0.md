# Nonlinear dependence

A constraint-based method learns a graph from independence tests. It is only as good as its test.
The default test, partial correlation, sees linear dependence only: when an effect bends, it can
miss an edge or add a false one. In 0.8.0, PC, FCI, GFCI, and CD-NOD take four tests that detect
nonlinear dependence: KCI, RCoT, CMIknn, and GPDC. TODO(numbers): one topline per test, "more than
N x faster than <package>", from the 0.8.0 card's finished cells.

## TL;DR

- Four nonlinear tests: `indep_test="kci"`, `"rcot"`, `"cmiknn"`, and `"gpdc"`, in `pc`, `fci`,
  `gfci`, and `cdnod`.
- TODO(numbers): speed against each reference package, from the 0.8.0 card.
- TODO(numbers): accuracy against each reference package, from the card.
- KCI and CMIknn run on a CUDA GPU: on one A100, PC ran 3.3-8.4x faster with KCI and 10-29x
  faster with CMIknn than on eight CPU cores, with the same graphs.
- Reorder your columns, and each test gives the same p-values: they follow the variables, not
  their positions.

## Four tests

Each test asks whether `x` and `y` are independent given a set of variables `z`. They differ in how
they measure dependence and in what they cost.

| `indep_test` | Test | How it decides | Cost |
|---|---|---|---|
| `"kci"` | Kernel conditional independence ([Zhang et al., 2011](https://arxiv.org/abs/1202.3775)) | Compares `x` and `y` in a Gaussian-kernel feature space after removing `z` | Grows with the square of the rows or faster; `rank=k` caps each kernel at `k` columns |
| `"rcot"` | Randomized conditional correlation ([Strobl, Zhang, and Visweswaran, 2019](https://arxiv.org/abs/1702.03877)) | Approximates the kernel test with random Fourier features | Linear in the rows; warns below 500 rows |
| `"cmiknn"` | Nearest-neighbor conditional mutual information ([Runge, 2018](https://proceedings.mlr.press/v84/runge18a.html)) | Estimates conditional mutual information and builds its null by shuffling `x` among neighbors in `z` | 500 shuffles per test by default |
| `"gpdc"` | Gaussian-process distance correlation ([Runge et al., 2019](https://doi.org/10.1126/sciadv.aau4996)) | Regresses `x` and `y` on `z` with Gaussian processes, then tests the residuals with distance correlation | Grows with the cube of the rows per regression; regressions are cached |

Each test's class, `KCI`, `RCoT`, `CMIknn`, and `GPDC`, takes its settings as arguments. To use
other settings inside a search, register a variant by name:

```python
from functools import partial

import andrey
from andrey.core.ci import make_indep_test, register_indep_test

register_indep_test("cmiknn_k5", partial(make_indep_test, "cmiknn", k_cmi=5))
fit = andrey.pc(data, indep_test="cmiknn_k5")  # data: your array of rows by variables
```

## How they run fast

- **Shared work.** KCI builds each conditioning set's kernel matrices once and shares them across
  every pair that uses it. GPDC caches its regressions.
- **Early stopping.** CMIknn stops shuffling once the p-value's side of `alpha` is certain. The
  p-values that PC ranks to orient colliders are always computed from every shuffle.
- **GPU.** With `backend="auto"`, KCI (in float64) and CMIknn run on a CUDA GPU above a size
  cutoff. On one A100 against eight CPU cores, PC ran 3.3-8.4x faster with KCI (5 to 10
  variables, 500 to 2,000 rows) and 10-29x faster with CMIknn (5 variables, 500 and 1,000 rows),
  with the same graphs. CMIknn's p-values on the GPU are the CPU's exactly; KCI's agree to within
  rounding. The first CUDA call in a process takes a few seconds, so the smallest KCI fit, 5
  variables and 500 rows, was slower on the GPU.

## The same p-values in any column order

RCoT's random Fourier features and CMIknn's shuffles are seeded by the seed and the variables of
each query, not their column positions, and every test holds its data in an order computed from
the columns' own values. Reorder your columns, and the p-values do not change. (From 2,000 rows, KCI
uses every BLAS thread, so its p-values repeat for a fixed thread count.)

## Limits

The four tests are experimental in 0.8.0: each warns with `ExperimentalWarning` on its first use
in a process. The 0.8.0 release card reports the cells our benchmark finished; the largest graphs
are not yet measured, and the tests become supported when their benchmark is complete.

## Other highlights

- **Background knowledge for every search.** TODO(pending review): required and forbidden
  edges and tiers in every method that searches, and `max_depth`.
- **One switch for column order.** TODO(pending review): one tie-break switch, and a page
  on how column order and machines enter each method.
- **Score defaults that follow the data.** BOSS, GRaSP, GES, hill climbing, tabu search, and
  exact search score categorical data with BDeu by default, and TODO(pending the mixed-data
  change) mixed data with the conditional Gaussian score. Before, both took the linear-Gaussian
  BIC, which on category codes raised errors on networks with dependent columns. This breaks the
  API: such data can give a different graph than in 0.7.0.
- **Faster categorical tests.** The chi-square, G-square, and conditional Gaussian tests answer many
  queries at once. PC with chi-square or G-square runs 4-6x faster than in 0.7.0 on the alarm,
  hepar2, and andes networks, with the same p-values and graphs.
- **BOSS and GRaSP on categorical data.** Both take the BDeu score and the categorical BIC.
- **Clearer errors.** PC, FCI, GFCI, CD-NOD, and the PCMCI methods name columns that copy another
  before any test runs, and degenerate inputs raise errors that say what to fix.
- **The same graph in any column order, on any machine.** Ties break by the data, not the column
  position or the CPU, in DirectLiNGAM, ICA-LiNGAM, MultiGroupDirectLiNGAM, ParceLiNGAM, exact
  search, GES, XGES, GIES, CALM, GIN, the PCMCI methods, and PC's and CD-NOD's colliders.
- **FCI's limits, measured.** The reference pages of FCI and GFCI give how many fits finish within
  the time limit up to 800 variables, and from what size their errors exceed the empty graph's.
