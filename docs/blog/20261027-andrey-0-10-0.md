# The boundary

In 0.9.0, the rocket lifted off: every method we sped up returns the same graphs in less time. This
is chapter two. How far does that speed take each method? Every method has a boundary. Past it, the
method either stops finishing, on time or memory, or finishes with a graph no better than the empty
graph, the graph with no edges. In 0.10.0, we map that boundary for every supported method, by the
number of variables, the number of rows, and how dense the graph is. BOSS finishes graphs of 1,600
variables with fewer errors than the empty graph, GRaSP 800, PC 400, and GES 400 once it has 10,000
rows.

## TL;DR

- A map for each method: the problems it finishes within the time cap and solves better than the
  empty graph.
- How far each family goes, at 2,000 rows and a mean degree of 2:
  - Permutation-based: BOSS to 1,600 variables, GRaSP to 800.
  - Constraint-based: PC to 400.
  - Score-based: GES, GIES, and XGES to 200, and to 400 with 10,000 rows; CALM to 400.
  - Linear non-Gaussian: DirectLiNGAM to 400.
- More rows move an accuracy boundary to the right; a denser graph moves it to the left.
- A boundary is a reference, not a hard limit: it moves with the data, the settings, and the
  machine.

## Two ways to stop

**It does not finish.** The work of a search grows with the number of variables and with how many
causes each one has. Past some size, a fit no longer finishes within our time cap of one hour, or
it runs out of memory.

**It finishes, but the graph is no better than nothing.** The empty graph is the simplest answer:
it draws no edges, so it misses every true edge and adds no false one. A method that makes more
errors than the empty graph has added more mistakes than it found edges. This happens when there are
too few rows for the tests or scores to tell an edge from noise, or when the graph is so dense that
each variable has more causes than the data can separate.

The second way matters as much as the first. A method that finishes in a second on 3,000 variables
is no help if its graph is worse than drawing none. So a problem is inside the boundary only when
the method does both: finishes, and beats the empty graph.

## Why the boundary is there

Most of the time goes to conditional independence tests. To decide whether two variables share an
edge, PC tests them given sets of their neighbors, first one at a time, then in pairs, triples, and
so on. The number of pairs grows with the square of the number of variables, and the number of
conditioning sets grows exponentially with the number of neighbors. So a denser graph costs far
more tests, and a larger one more again. The score-based and permutation-based searches face the
same growth in the candidate parent sets they score.

Too many tests also cost accuracy. A test given a large conditioning set has few rows for each
degree of freedom, so it loses power, and each wrong answer removes or keeps an edge that later
steps build on. This is why a dense graph can stop a method on accuracy before it stops on time.

Read a cell's color as how much better than the empty graph the method does: the stronger the color,
the fewer errors. A gray cell is a problem where the method finishes but does no better than the
empty graph. A mark is where a row stops: a cross at the time cap, a square at the memory cap, an
exclamation mark when the fit fails, for example when there are fewer rows than variables, and a
circle past the accuracy boundary, after two sizes in a row that do not beat the empty graph. Larger
problems would only cost time to show the same. The line around the colored cells is the boundary.

The maps show two kinds of boundary. Most score-based searches stop on accuracy: with more rows
they reach further, GES from 50 variables at 500 rows to 400 at 10,000, while on a graph with a mean
degree of 8 GES, XGES, tabu search, and hill climbing do no better than the empty graph even at 20
variables. The permutation-based searches, exact search, and CALM stop on time: BOSS stays accurate
up to 1,600 variables, and more rows cost it time, so at 10,000 rows it reaches 800. PC stops on
accuracy past 400 variables at every row count. On denser graphs PC beats the empty graph further,
but by less, because the empty graph then misses many more edges; hover a cell for its share.

## And beyond

0.9.0 made each test and score cheaper, and 0.10.0 shows how far that goes. To go much further, a
method has to run fewer tests, and to use the sparsity of real graphs. Both are active research:

- **Fewer tests.** [Shiragur, Zhang, and Uhler (2024)](https://arxiv.org/abs/2406.01823) learn a
  coarser causal graph with a polynomial number of tests, one that equals the true graph when the
  true graph is identifiable. [Kim and Lee (2026)](https://proceedings.mlr.press/v337/kim26a.html)
  deduce the answers of many high-order tests from lower-order ones instead of running them, so a
  search runs fewer tests and fewer of the weakest ones.
- **Sparsity.** PC stays feasible on high-dimensional data when the graph is sparse
  ([Kalisch and Bühlmann, 2007](https://www.jmlr.org/papers/v8/kalisch07a.html)): when each
  variable has few neighbors, the number of tests grows polynomially, not exponentially, with the
  number of variables. Spread over the cores of one machine, such a search reaches thousands of
  variables ([Le et al.](https://doi.org/10.1109/TCBB.2016.2591526)).

Very large causal discovery, sparsity used to reach millions of variables, is a stage of our
[roadmap](../docs/roadmap.md). The boundary in this post is where that work starts.

## Limits

- **A reference, not a hard limit.** A boundary holds for what we measured: our simulated graphs
  and data (Erdos-Renyi graphs with linear relations, standardized), the sizes and densities above,
  each method's settings, and our machine. Most methods run at their defaults; BOSS and GRaSP run
  with a BIC penalty of 4, and GES with a limit of 4 parents. The release card lists every
  setting. Another graph structure, other data, other settings (a smaller `alpha`, a `max_depth`),
  or more cores can move it either way. Use it to know where to start, then measure on your own
  data.
- **Time.** The cap is one hour per fit. A longer cap moves the time boundary to the right; it
  does not move the accuracy boundary.
- **Other axes.** FCI and GFCI, whose rows grow with the variables, and the latent-variable,
  time-series, and pairwise methods are measured on their own axes; the release card lists them.
