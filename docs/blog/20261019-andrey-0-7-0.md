# Permutation invariance

Give two people the same table with its columns in different orders. Ask each to learn a causal
graph. They should get the same graph. Column order carries no information: it comes from a database
export, a DataFrame, or whoever wrote the CSV. A method whose graph does not depend on that order is
permutation invariant.

Strictly, such a method is permutation equivariant: reorder the columns, and the graph's nodes
reorder the same way. Here, "the same graph" allows for that relabeling.

Many causal-discovery methods are not invariant. When two steps look equally good, they take the
first one they find, and "first" means the leftmost column.
[Colombo and Maathuis (2014)](https://jmlr.org/papers/v15/colombo14a.html) showed this for PC. It
matters for three reasons:

- **Reproducibility.** Two analysts with the same data get different graphs.
- **Trust.** An edge that flips when you reorder the columns was never supported by the data.
- **Benchmarks.** Data generators often write columns in an order tied to the graph, so a method
  that favors the first column gains or loses accuracy it did not earn.

In nine of our methods, we replace choices tied to column order with choices tied to the data. Our
benchmark also shuffles columns to keep their order from skewing the results.

## TL;DR

- Andrey 0.7.0 brings permutation invariance to PC, FCI, GFCI, CD-NOD, hill climbing, tabu search,
  BOSS, GRaSP, and GIN: reordering the columns in your dataset no longer changes the discovered
  causal graph.
- Permutation invariance is a core feature of Andrey, and we are bringing it to every method.
- By eliminating sensitivity to arbitrary column ordering, Andrey makes causal discovery more
  reproducible, reliable, and trustworthy.

## How we found it

It started with hill climbing. On the 0.6.0 categorical benchmark, pgmpy's hill climbing had fewer
errors than Andrey's on 17 datasets. We went looking for a bug and found a tie: adding `x -> y` and
adding `y -> x` can score exactly the same, and Andrey gave the tie to whichever column came first.
Reverse the columns, and Andrey had no more errors than pgmpy on 14 of the 17.

Then we checked our own data. Our generators wrote columns in an order tied to the graph: on a
scale-free graph, the biggest hub came first. That order misled us. A better PC rule looked worse
until we shuffled the columns.

## Why it happens

Column order enters when a method takes the first of two equally good steps. In PC, two colliders
can disagree about one edge, and whichever PC orients first wins.

Below, A causes B, C, and D, and each of them causes E. A and E look independent given B, with a
p-value of 0.052, just above the significance level of 0.05, so PC also proposes two false
colliders, `A -> C <- E` and `A -> D <- E`. The column-order rule visits colliders by the column
they point into, left to right: whenever C or D sits left of E, a false collider wins. The p-value
rule starts with the most clearly separated pair, so the true colliders always win.

Click a column to move it first, or shuffle them all.


The same thing happened in hill climbing and tabu search (score ties), BOSS and GRaSP (a starting
order taken from the columns), GIN (a test built from each cluster's first column), and FCI and GFCI
(rules and a search step that visit the columns in order).

## How we fixed it

Each fix replaces a column's position with a value computed from its data, which moves with the
column.

- **PC.** Conflicting colliders are oriented by the p-value that separated each pair, highest first,
  adapting [Ramsey (2016)](https://arxiv.org/abs/1610.00378). Meek's rules then apply in rounds, so
  an edge they disagree about stays undirected. In 16 settings, no reordering changed PC's graph,
  and PC made fewer errors in every one, for at most about 4% more time.
- **Hill climbing and tabu search.** Exact score ties go to a rank computed from each column's data.
  Accuracy is unchanged.
- **BOSS and GRaSP.** Both search the columns sorted by that rank. Their accuracy matches
  causal-learn's.
- **GIN.** The test that orders the hidden causes uses every member of a cluster, not the first.
- **FCI and GFCI.** Their rules apply in rounds, and the possible-d-separation step visits the
  columns by rank. `possible_dsep="fast"` keeps the column-order step.
- **Benchmark data.** Our data generators and `andrey.data.load_dataset` shuffle the columns along
  with the true graph.

Simulated data can understate the problem, so we also ran FCI on six real tables, each under 200
random column orders (20 for the full superconductivity table). With the default, no order changed
the result.

## How Andrey compares

Permutation invariance is a yes-or-no property, so a few small examples answer it. We fit each
package's implementation at its defaults on three small datasets per method, each in nine column
orders, and checked whether any reordering changed the graph.

```{raw} html
:file: 0.7.0/compare.html
```

For BOSS, GRaSP, GIN, and tabu search, every other implementation we checked changed its graph under
some reordering. pcalg and causal-learn can make PC's colliders order-independent, but only with
options that are off by default; Andrey does it by default, with no extra tests.
